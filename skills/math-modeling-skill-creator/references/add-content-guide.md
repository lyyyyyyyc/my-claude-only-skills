# 为 `math-modeling-skill-creator` 新增内容的维护指南

## 用途
这份文档是给 Codex 在后续继续扩展 `math-modeling-skill-creator` 时使用的维护规程。以后如果需要继续往这个 skill 里新增触发规则、结构设计原则、维护流程、测试提示词设计建议或安装闭环要求，优先先读这份文档，再决定改哪里、怎么改。

## 什么时候应该新增内容
以下情况适合继续新增到这个 skill：
- 出现新的高频“创建数模 skill / 改已有数模 skill / 设计 skill 模板”的用户表达，导致当前 `description` 或 `when_to_use` 覆盖不足。
- 需要补新的触发设计原则、结构设计原则或 references 分层规则。
- 需要补新的维护规则，例如“什么时候扩展已有 skill，什么时候新建 skill”。
- 需要补新的轻量测试提示词设计方法。
- 发现新的常见跑偏错误，值得加入 `Common Mistakes` 或清单文档。

以下情况通常不应该直接加到这个 skill：
- 某个具体数模题的解法细节。
- 某个单一模型的方法说明。
- 外部 `skill-creator` 的完整 benchmark / viewer / run_loop / packaging 流程细节。
- 一次性会话里的临时偏好。

## 新内容应该加到哪里
新增内容时，先判断它属于哪一类，再放到对应区块：

| 新增内容类型 | 应放位置 |
|---|---|
| 触发词、用户口语表达、何时应该调用本 skill | `description` / `when_to_use` |
| skill 创建器触发后的第一步行为 | `什么时候优先用本 skill` / `第一优先动作` |
| 需求拆解与边界确认规则 | `目标与意图捕获` |
| 如何写 frontmatter、如何做触发设计 | `触发设计（description / when_to_use）` |
| 主文 / references / agents 如何分层 | `结构设计（主文 / references / agents）` |
| 是否新建 skill 还是扩展现有 skill | `数模 skill 分工判断` |
| 测试提示词与轻量验证 | `轻量测试提示词设计` |
| 修改已有 skill 的策略 | `修改已有 skill 的维护原则` |
| 低频长说明、检查清单 | `references/` |

## 新增内容的判断流程
以后新增内容时，按下面顺序判断：

1. 先判断这是“触发优化”还是“结构/维护知识扩展”。
2. 再判断它是通用规则，还是只适用于某一种数模 skill。
3. 如果只是低频长说明，优先放进 `references/`，主文只留短入口。
4. 如果会改变触发边界，必须同步检查 `description` 和 `when_to_use`。
5. 如果内容本来属于某个具体数模 skill，而不是 skill 创建器本身，就不要写进这里。

## 写法规范
- 解释“为什么这样设计”，不要只堆“必须”。
- 新规则优先短句化、归入已有区块，不轻易新开大区块。
- 不写一次性案例总结，不写叙事式历史。
- 不整包复制外部 `skill-creator` 或 `writing-skills`，只提炼对数模 skill 创建最有用的部分。
- 先提升可维护性，再提升完整性；宁可少而稳，不要大而乱。

## 修改前检查清单
- 这条内容是否真的是高频、可复用的数模 skill 创建规则。
- 是否和已有区块重复。
- 是否本来应写到某个具体 `math-modeling-*` skill，而不是 `math-modeling-skill-creator`。
- 是否会改变触发边界。
- 是否需要同时更新 `skill-creation-checklist.md`。

## 修改后检查清单
- frontmatter 是否仍然清楚表达“创建/修改数模 skill”的定位。
- 新内容是否放在了正确区块。
- 主文是否仍然以“触发设计 + 结构设计 + 维护原则”为主，而不是被长说明压重。
- 是否引入了新的重复表述。
- 是否需要新增 2–3 条测试提示词来验证这次修改。

## 常见错误
- 把数模 skill 创建器写成数模求解器。
- 把外部通用 skill 的完整执行流水线全部复制进来。
- 只教“怎么写正文”，不教“怎么设计触发边界和 references 分层”。
- 不先判断该需求应新建 skill 还是扩展已有 skill。
- 修改后不检查 `description` / `when_to_use`。

## 维护时的默认原则
- 能少改就少改，优先最小改动。
- 先设计触发，再设计结构，最后才是正文细则。
- 低频长说明优先下沉到 `references/`。
- 对数模 skill 创建器来说，最重要的是“可维护结构”，不是“最长说明书”。

## 建议回归测试提示词
- “帮我创建一个专门做数模约束提取的 skill。”
- “我想修改已有的数模论文写作 skill，顺便优化触发词。”
- “帮我做一个数模 skill 模板，后面可以继续扩展 references。”

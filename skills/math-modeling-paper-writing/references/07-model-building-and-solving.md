# 模型的建立与求解写作要求

## 最高优先级交付门禁：仅在完整正文写完时询问 BZD

本门禁只服务于一个明确节点：**某一问的“模型建立与求解论文正文”首次完整写完，或按用户要求被整篇完整重写完毕。** 不得因为任务涉及该问题、修改了配套文件，或局部调整了正文，就重复询问。

### 唯一触发条件：三项必须同时满足

只有同时满足以下三项，才触发 BZD 询问：

1. **任务对象正确：** 用户本轮的主要交付目标明确是“写完整的问题一、问题二或问题三模型建立与求解论文正文”，而不是 Notebook、结果表、方案文档、摘要、自查报告或普通复审。
2. **完成方式正确：** 本轮将原本不存在或尚未完成的正文写成了完整正文；或者用户明确要求“整篇重写该问的模型建立与求解正文”，且本轮确实完成了全文替换。仅修改部分段落不满足此项。
3. **完成状态正确：** 该问正文所需的建模思路、模型公式、求解方法、求解结果与解释均已写入正文载体，并已达到可交付状态。仍在写作中、只完成局部小节或只补占位内容时不触发。

“实质性修改”本身不再是触发条件。即使修改了公式、模型口径、结果数值或图表解释，只要不是按用户要求完成整篇正文的新建或全文重写，就不得触发询问。

### 明确不触发的任务

以下情况一律按普通交付流程结束，不询问 BZD：

- 新建、修改、调试或复审 Notebook、代码、数据、结果表、参数文件和图片；
- 根据评委审查、BZD 自查或报错结果修正若干问题；
- 修改已有正文中的局部公式、段落、数值、表格、图片、图表解释、结论口径、引用、错别字或格式；
- 将新运行结果同步进已经写完的正文；
- 编写或修改详细建模方案、求解结果摘要、专项自查报告、执行计划或数据说明；
- 审查、解释、评价或讨论已有正文，但没有完整新建或全文重写正文；
- 修改本 skill、路由文件或其他技能规则；
- 同一版完整正文已经询问过并得到用户“是/否”决定，之后进行补丁式修改、复审修正或结果更新。

### 完成事件与防重复规则

1. 不得在开始修改文件时预先登记 `BZD 专项自查询问：待执行`。应在全部工作结束后，根据上述三项条件判断本轮是否真的产生了“完整正文写完事件”。
2. 每一问的每次完整正文写完事件最多询问一次。用户已经针对该完成事件回答“是”或“否”后，后续局部修订不得再次询问。
3. 只有用户后来明确要求“整篇重写该问的模型建立与求解正文”，并且本轮完成了新的全文版本，才产生新的完整正文写完事件。
4. 若只是无法确定修改是否算“整篇重写”，默认按不触发处理，不能为了保险而多问一次。

### 触发后的执行方式

满足唯一触发条件后，最终回复可以先简短说明交付内容，但最后一段必须逐字使用下面的问句，并在问句后立即结束：

`问题 X 的模型建立与求解已经写完，是否需要调用 bzd-model-solution-checker 进行自查？请回答是或否。`

将 `X` 替换为“一”“二”或“三”。如果同一轮完整写完多问，则从最先完成且尚未询问的问题开始，一次只处理一问。用户回答“是”后调用 `bzd-model-solution-checker`；回答“否”则不调用；回答不明确时再继续确认。

### 最终回复发送前判定

```text
本轮主要目标是写完整的模型建立与求解论文正文？
├─ 否：普通交付，不询问
└─ 是：本轮是否完成首次全文或用户明确要求的整篇重写？
   ├─ 否：普通交付，不询问
   └─ 是：正文是否已经完整可交付？
      ├─ 否：仍在写作，不询问
      └─ 是：同一完成事件是否已经询问过？
         ├─ 是：普通交付，不重复询问
         └─ 否：最终回复以固定 BZD 问句结束
```

该判定的核心是“完整正文写完事件”，不是“碰过正文文件”。修改范围再大，只要属于已完成正文的后续修正，而非完整新建或明确的全文重写，都不触发。

## 这一部分写什么
- 这是整篇论文最长、最核心的部分。
- 本部分既要回答“模型怎么建”，也要回答“模型怎么求”，还要解释模型中的变量、约束、目标和算法步骤在本题中的实际含义。
- 问题一、问题二、问题三的模型建立与求解分别作为三个独立的一级部分，固定写为：
  - `六、问题一模型建立与求解`
  - `七、问题二模型建立与求解`
  - `八、问题三模型建立与求解`
- 每个一级部分内部再按需要设置“建模思路、模型建立、求解方法、求解结果或结果分析”等二级小节；不得再用 `6.1`、`6.2`、`6.3` 分别代表问题一、问题二、问题三。
- 不得单独设置“变量与参数定义”小节，也不得在“模型建立与求解”部分制作专门的变量、参数、输入输出或符号定义表。变量与参数应在“模型建立”中首次进入正文或公式时用连续文字就近解释，完整符号汇总沿用前文“符号说明”，避免重复列表割裂公式推导。若确需展示超参数、经济情景参数或求解器配置，只能制作服务于参数取值、比较或复现的参数表，不得用表格替代变量的正文说明。
- 不得单独设置“本问结论”小节。本问最终得到的数值、方案、排名、预测或决策应直接落在“求解结果”或“结果分析”中，不再在章节末尾重复总结。
- 若原提纲中存在“6.2 变量与参数定义”“6.7 本问结论”或问题二、问题三的对应小节，应删除这些标题，并对保留的小节连续重排编号，不得保留空号。
- 若三问共用一个主模型，仍须保持三个一级部分。问题二、问题三可以明确继承前问模型，并集中说明新增约束、参数变化、目标调整或输入输出联动，不必把完全相同的模型从头抄写一遍。

## 建模写法要求
- 分析必须出现在所建立模型之前，不要跳过分析直接给公式。
- 模型必须明确，不能让评委自己去你的文字里“找模型”。
- 关系式一定要写清楚，整体思路要清晰、易读易懂。
- 建模与求解要明确分开，避免“模型、算法、结果”混成一段。
- 公式前先说明：为什么需要这个模型、变量代表什么、目标是什么。
- 公式后要解释：每个约束在题目里限制了什么。
- 数学公式必须足够可核查，让读者在不看代码的情况下也能看清模型口径、优化方向和可行域；具体完整项按下文“变量、参数与核心数学关系”和“公式充足度的最低检查项”执行。
- 如果多个小问相似，仅新增约束或改变目标，优先使用“主模型 + 改进模型”结构，不要机械地把模型从头写三遍。
- 基本模型应尽量做到：完整、正确、简明。不要一上来就堆复杂变体，先把主模型立稳。
- 如果使用了简化模型，必须明确说明：
  - 为什么要简化；
  - 简化依据是什么；
  - 简化后保留了哪些核心关系，舍弃了哪些次要因素。
- 模型设计应以“解决问题有效”为优先，不追求数学形式上的高深和复杂。
- 默认遵守以下取舍原则：
  - 能用初等方法解决的，不优先引入更高级的方法。
  - 能用简单方法解决的，不优先引入更复杂的方法。
  - 能用多数评委看得懂的方法说清楚的，不优先用少数人才能快速理解的表达。
- 允许创新，但创新应服务问题，不要为了“显得厉害”而离题堆术语或堆模型。
- 论文中的创新可以落在：
  - 建模结构本身；
  - 简化策略；
  - 求解方法；
  - 结果表示与检验；
  - 推广方式。

## 建模步骤展开建议
- 若本节内容较长，推荐按下面 4 段自然展开：
  - 建模思路
  - 模型建立
  - 求解方法
  - 求解结果与分析
- `建模思路` 主要回答：
  - 对问题做了哪些详细分析；
  - 对模型中参数做了哪些解释；
  - 完成内容所必需的公式推导、图表或结构示意有哪些。
- `模型建立` 主要负责把模型正式写出来，并对关键公式、变量、约束和目标给出必要解释。
- `求解方法` 主要负责把求解思路写清楚；最好像写算法一样，按步骤说明如何把模型真正算出来。
- `求解结果与分析` 直接给出回答题目所需的数值、方案、排序、预测或决策，并解释其实际含义；该小节已经承担本问收束作用，不再另设“本问结论”。

## 建模思路与模型选择
- 本节承接“问题分析”中已经完成的任务拆解，不重复抄写题意。每个小问进入模型前，先用一小段明确：本问目标、已知条件、预期输出及其数学形式。
- 只分析本题实际存在的数据或决策特征，例如时序性、非线性、多目标、整数决策、随机性、空间关系、动态状态或网络结构；不要为了显得全面而把所有特征机械罗列一遍。
- 模型选择必须形成“题目特征 -> 模型能力 -> 选择理由”的对应关系，并说明经典模型针对本题做了哪些适配，例如改变目标函数、增加业务约束、重新定义参数、调整损失函数或嵌入前问输出。
- 若确实比较过备选模型，应交代候选路线、统一比较口径、关键证据和最终选择理由；若没有真实比较，不得虚构“经过多次比较最终选定”。
- 使用“针对性判定”：删除赛题对象、数据口径和业务约束后，如果该段仍可原封不动用于大多数题目，说明它只是在介绍通用模型原理，必须补入本题变量、参数、约束或调整动作。
- 推荐表达骨架：`问题 X 要求【目标】。根据【已知条件】与【数据/决策特征】，该问题可归为【数学任务】。考虑到【适用理由】，采用【模型】求解，并针对【本题特点】调整其【目标函数、约束、状态关系、损失或参数】。`

## 按题型选择模型建立写作套路
- 以下内容是论文组织模板，不是方法选择清单。实际模型应来自用户已经确认的建模结果，或由模型与方法 SKILL 生成并经用户确认；若材料中尚未确定模型，不得由论文写作 SKILL 凭模板擅自选定，应先补齐模型方案再写正文。
- 确定实际模型后只选择一个主套路；若题目是混合型问题，明确主套路和补充套路的关系，不要把所有模板机械叠加。
- 每个套路都应落到“研究对象 / 模型表达 / 求解动作 / 结果证据”四个层面。截图中的方法名称和参数只是示例，正文必须替换为本题实际使用的方法和最终配置。

### 评价类模型
1. **构建指标体系**：列出指标名称、指标类型、实际含义、效益方向和数据来源；说明成本型指标如何转化为可比较的正向指标，并给出相应处理结果。
2. **确定指标权重**：根据实际使用的赋权方法写出计算链。若使用熵权法，应依次呈现标准化、比例、熵值、差异系数和归一化权重；若使用 AHP、CRITIC 或组合赋权，则只写实际方法。每一步保留必要的中间结果表，避免只报告最终权重。
3. **进行综合评价**：根据实际评价方法呈现评分、排序或分级链。若使用 TOPSIS，可按加权矩阵、正负理想解、距离、贴近度和排名组织；每个环节只保留能支撑下一步的公式或中间表。
4. **解释结果**：说明排名或等级意味着什么，并指出指标方向、权重来源和标准化方式对结论的影响。评价类方法不是固定的“熵权法 + TOPSIS”组合，不能因模板存在而强行套用。

### 预测类模型
1. **说明特征工程**：交代特征筛选、变换、滞后构造或降维的实际操作及理由。Pearson、互信息等只是可选方法；若使用，应展示筛选前后特征集合或指标对比表。
2. **呈现模型与参数**：给出实际模型的必要数学表达，说明参数、超参数、拟合参数和求解器参数的区别，并用参数表记录最终值、选择依据和验证方式。最终超参数由用户或建模流程确定，不能由论文写作 SKILL 擅自补全。
3. **展示验证结果**：根据任务类型报告训练 / 验证过程、测试集指标和至少一个合理基线。训练曲线只在模型确实有迭代训练过程时使用；时间序列必须保持时间顺序，不能把普通随机 K 折当作默认方案。
4. **连接预测结论**：明确指出模型相对基线改善了什么、误差是否满足题目要求，以及哪些结果可以支持后续决策；MAPE 在真实值为零或接近零时不能直接使用。

### 优化类模型
1. **先集中呈现模型三要素**：在展开算法前，先用一个集中公式块给出决策变量、目标函数和约束条件；必要时补充变量取值范围、归一化和罚项。这样评委能先看清“优化什么、受什么限制”。
2. **解释约束的实际含义**：逐类说明容量、访问、时间窗、流量守恒、资源或业务规则等约束如何对应题目条件，不只罗列不等式。
3. **展开求解算法**：按实际算法说明编码或初始化、可行性处理、目标 / 适应度计算、更新或交叉变异、终止条件和输出。若使用遗传算法、粒子群或模拟退火，补充参数表、收敛曲线和与基线或其他方案的对比；若使用精确求解器，则改写为求解器输入、求解流程和状态输出，不要套用启发式算法模板。
4. **解释方案结果**：把最优目标值、关键决策变量和约束满足情况落到表格或图中，并说明方案如何回答题目，而不是只写“算法收敛”。

### 机理分析类模型
1. **先画机理框架**：用变量关系图或流程图说明核心变量、输入、输出和控制关系；若问题确实涉及 ODE / PDE，再在此基础上引出控制方程。
2. **建立关键关系**：逐条给出关系式、推导依据和参数辨识方法。参数来源要区分文献、实验拟合、统计估计和题目给定值，不能把辨识结果写成无来源常数。
3. **联立求解与验证**：说明方程如何整合、边界或初始条件如何处理、采用什么方法求解，并用真实观测或题目数据对比验证结果。机理分析的重点是“关系如何解释现象”，不是为了形式完整而堆叠方程。

### 套路交付检查
- 是否选定了一个主模型套路，并说明了与其他小问的衔接。
- 是否同时交代了模型表达、求解动作和结果证据，而不是只写方法名称。
- 是否把参数表、结果表、流程图、收敛图或验证图放在对应论证附近，并在正文中解释其用途。
- 是否由 `math-modeling-model-and-methods`、`math-modeling-intelligent-optimization-coder` 或超参数调优 SKILL 负责生成或确认专业内容，并由本论文写作 SKILL 把最终公式、参数和必要算法说明完整整合进正文；不能因调用了其他 SKILL 就省略论文中的可核查信息。

## 变量、参数与核心数学关系
- 建模前先建立内部“变量与参数账本”，至少区分决策变量、状态变量、输入变量、输出变量、集合、下标和固定参数，并记录其符号、含义、单位、取值范围及来源。正文只呈现读者理解模型所必需的内容，完整符号表仍按 `references/05-symbols.md` 执行。
- 变量或参数首次进入正文或公式时必须解释；模型修改后同步清理失效变量、旧符号和旧单位，不能让已经废弃的定义继续留在符号表、公式、图表或代码说明中。
- 根据实际问题建立核心数学关系，可包括目标函数、约束条件、状态方程、回归关系、评价指标、概率分布、损失函数或机理方程。公式前说明建模依据，公式后解释各项在本题中的实际含义和作用。
- 参数来源必须可追溯，并明确属于哪一种：题目或附件直接给定、由数据统计/回归/辨识得到、由优化/实验/仿真确定、由文献/领域经验/明确假设给出。估计值、预测值和假设值不得静默写成题面已知常数。
- 每类约束都要对应现实含义，例如资源、容量、预算、时间、平衡、非负、整数、逻辑、边界或业务规则；不能只列不等式而不说明它限制了什么。
- 本节中的符号、大小写、上下标、标量/向量/矩阵身份、单位、百分数与 `0–1` 口径，必须与符号表、前后问题、公式和图表保持一致；同一符号只能表示一个含义，前问输出进入后问时不得随意改名。
- 本节完成后对核心符号、跨问变量和单位执行一次全文检索，核对符号表、正文、公式、图表及前后问题，并清理模型修改后遗留的旧符号和旧单位。

## 多问题输入输出联动
- 多个问题存在递进关系时，必须把联动写成可核查接口，而不是只说“基于问题一”。建议先建立下表，再据此写正文：

| 上游问题 | 输出量或结果文件 | 数学形式与单位 | 下游用途 | 必要转换 | 不确定性处理 |
|---|---|---|---|---|---|
| 问题一 | 指标、权重、分类或参数 | 标量/向量/矩阵/集合 | 问题二的输入、初值、参数或预测变量 | 标准化、聚合、映射等 | 误差区间、情景或敏感性 |
| 问题二 | 预测、估计或方案结果 | 与实际结果一致 | 问题三的目标函数、约束或情景设置 | 单位、时间尺度或坐标转换 | 传播误差或鲁棒处理 |

- 联动必须实际体现在变量、参数、目标函数、约束、初始值、基线、验证器或数据输入中；后问若重新使用原始数据独立计算，应如实说明，不能伪装成递进关系。
- 明确数据、符号、单位、时间尺度、空间坐标和统计口径是否发生转换。只要上游输出含有估计或预测误差，且该误差会进入下游目标、约束、参数或结论，就必须说明传播影响，并至少采用区间、情景、概率分布或敏感性分析中的一种方式承接不确定性。

## 目标函数与约束条件的集中表达要求
- 对优化模型，默认不要把目标函数、约束条件、归一化公式、罚项公式分散得太开。若前文为了讲推导已经分散写出，后文应尽量再补一个“集中公式表达”小节，把完整模型重新收拢一次。
- 这个“集中公式表达”小节优先包含以下顺序：
  - 决策变量与辅助变量
  - 由变量诱导出的关键统计量或中间指标
  - 目标函数
  - 约束条件
  - 变量取值范围
  - 若使用启发式或 GA，再补“实际适应度函数与理论优化模型的关系”
- 若是遗传算法、粒子群、模拟退火等启发式算法，正文里允许先给“程序直接使用的适应度函数”，再给“论文层面的显式优化模型”；但二者之间必须说明对应关系，不能只给其中一边。
- 若算法本身直接优化的是隐式编码而不是显式整数变量，也应尽量补出等价的显式变量定义，用来把目标函数和约束条件整理清楚。
- 目标函数和约束条件写在一起的目的，不是重复堆公式，而是让评委能够一眼看到“优化什么、受什么限制、变量怎么取值、罚项怎么介入”。
- 集中表达前可用一句话概括：“综上，综合考虑【目标要求】及【资源、时间、容量等限制】，建立如下【模型名称】。”随后在同一公式块中列出目标函数、全部同层级约束和变量域，并在公式后逐类解释。
- 禁止只在前页单独给出目标函数、把约束散落在多处后直接进入算法，或用“约束条件见参数设置”等文字代替数学约束。

## 公式充足度的最低检查项
- 起草“模型的建立与求解”后，至少自查下面 6 项是否都在正文中有明确数学表达：
  - 变量或集合是否定义了；
  - 核心关系式是否写了；
  - 目标函数是否明确写成公式；
  - 约束条件是否成组列出；
  - 归一化、评分或罚项是否写清楚；
  - 变量取值范围或可行性条件是否交代了。
- 所有与当前模型适用的项目都必须满足；其中优化模型的决策变量、目标函数、约束条件和变量取值范围不得缺失。任一必需项缺失时都应继续补写，而不是直接进入结果段。
- 若模型已经有较多分散公式，但完整模型仍不易快速看懂，默认继续补一个“集中公式表达”小节，而不是假设评委会自己把它们拼起来。

## 建模推导与论证的表达补充要求
- 问题分析和公式推导过程要尽量做到：
  - 分析中肯、确切；
  - 术语专业、稳定；
  - 原理和依据正确、明确；
  - 关键步骤列出，避免一句话跳完全部推导。
- 忌讳：
  - 外行话；
  - 专业术语用而不明；
  - 段落冗长但关键依据不清；
  - 公式很多但逻辑链断裂。

## 求解写法要求
- 先写清算法或求解器名称、基本思想及其适用于本题的理由，再按“输入 -> 初始化/编码 -> 可行性处理 -> 核心计算或更新 -> 终止判定 -> 输出 -> 验证”展开。不要照抄教材或网页，也不要只写一句“采用某算法求得”。
- 至少交代算法输入、输出、关键步骤、核心参数、停止条件，以及实际使用的软件/编程语言和必要版本信息；初始值、初始种群、最大迭代次数和随机种子仅在随机、迭代或初始化敏感的算法中填写，使读者能根据正文复现主要计算过程。
- 起点、终点、节点、状态、路径、适应度、染色体、粒子等算法术语，必须转译成本题对象；同时说明选择该算法的题目依据，而不是因为“该算法应用广泛”。
- 智能优化算法还应按实际方法补充：解的编码与初始种群、适应度函数、可行性修复或罚项、选择/交叉/变异或位置更新规则、种群规模、学习因子/惯性权重/温度衰减等关键参数、多次独立运行结果与收敛曲线。没有使用的算子不得套模板补写。
- 若采用精确求解器或现成软件，改为说明选择理由、模型输入、求解模块、关键参数、求解状态和输出结果；不能把求解器当作黑箱按钮。
- 若求解依赖现成算法、命题、定理或经典结论，应说明引用依据及其在本题中的作用；必要的论证要让读者看清为何能够使用。
- 正文保留核心伪代码、关键步骤或求解流程图，完整可运行代码放入附录。程序不能代替模型、求解过程和结果说明。
- 若求解链路较长、模块较多或前后存在多阶段衔接，优先补一个简明流程图或计算框图；大段中间输出留在附录，正文保留影响结论的中间结果。
- 禁止使用“将数据导入 Python，求解结果如下”一类写法，因为它没有说明算法思想、参数配置、停止条件和结果如何产生。
- 本部分最终必须落到“算出了什么数值、方案、排序、预测或决策”，不能停在“该算法能够求解”。

## 求解结果呈现要求
- 逐项回扣题目任务，明确给出具体数值、方案、排名、预测或决策；明显结果也要写明，不能让读者自行从公式、程序或图表中推断。
- 每个关键结果逐项标明适用的对象、单位、统计口径、时间范围、样本范围和必要小数位；某字段确实不适用时可以省略或注明“不适用”。排序或分类结果说明方向，预测结果说明预测期，概率与百分数口径保持一致。
- 解释结果是否符合现实规律，并分析异常值、反常变化或与预期不一致的原因；随后说明实际意义、适用范围和局限性。
- 结果分析不能逐字重复图表中的全部数字。正文应提取关键数值、主要变化规律、组间差异、拐点或稳定区间，并说明这些证据如何回答题目。
- 对支撑结论所必需的中间结果，应在正文中保留；大段过程数据和完整明细表移入附录，不能把核心结果一股脑丢进附录。

## 图表分工、引用与去重
- 表格优先承载精确数值、参数和少量方案对比；图形优先展示趋势、分布、时间序列、变量关系、空间差异、流程或结构。详细排版规范继续按 `references/13-charts-and-figures.md` 执行。
- 同一组结果原则上选择一种主要表达。若图用于展示趋势、表用于核对精确数值且二者都必要，可以同时保留；否则正文保留图和少量关键数值，把完整表移至附录。
- 每个图表必须先于对应解释段落出现，并与解释紧邻。默认顺序为“图/表主体及题注 -> 解释段落”；解释段落再使用“由图 X 可知”或“由表 X 可知”分析主要结论。禁止先写解释后补图表，也禁止只放图表而不作说明。
- 正文表格原则上不超过 `15` 行。超过时优先展示代表性结果、统计摘要或前后若干行，也可以改用图形，并将完整表放入附录；若赛题或期刊模板另有要求，以模板为准。
- 推荐表达骨架：先放置 `【图/表主体及题注】`，随后写 `由图 X（或表 X）可知，【关键趋势或差异】，因此模型在【适用区间】内【结论】。`

## 参数、算法与摘要的交接记录
- 论文正文应区分模型参数、超参数、求解器参数、随机参数和业务参数，不要把它们统称为“参数”。
- 关键配置建议记录为：参数名、类型、符号、最终值、候选范围、选择或拟合方法、验证方案、随机种子、单位和敏感性结论。
- 最终超参数由用户或建模流程确定；本参考文档只要求准确记录，不替用户擅自选择或修改最终值。搜索范围和调参实验交给专门的超参数调优 SKILL。
- 参数记录、正文求解步骤、代码实际配置和结果文件必须相互一致；仅在相应算法适用时记录随机种子、初始种群或迭代参数，不适用的字段不强行填充。
- 优化算法还应说明理论优化模型与程序实际使用的适应度函数、罚项或修复规则之间的对应关系。
- 摘要只压缩呈现核心方法、关键求解动作和最终结果；完整公式、算法步骤、参数表和搜索过程留在本节或附录。

## 不要写什么
- 不要把算法原理全文照搬。
- 不要只列公式，不解释变量和约束含义。
- 不要只说“用某算法求解”，却不写求解步骤或参数。
- 不要单独设置“变量与参数定义”小节，也不要在模型建立部分单独制作“变量定义表”“参数定义表”“主要量定义表”或同类表格；变量与参数应在模型建立及公式附近用连续文字就近说明。参数比较表、超参数记录表和业务情景表仅用于展示实际取值、选择依据或敏感性结果，不能承担变量释义功能。
- 不要单独设置“本问结论”小节；最终答案应并入求解结果或结果分析。

## 常见扣分点
- 模型和题意脱节，看不出公式是怎么回答题目的。
- 算法解释没有转译成本题语义。
- 每个小问都重建一个模型，导致结构冗余且逻辑松散。
- 公式很多，但结果怎么出来的说不清。
- 公式太少，导致正文只有方法说明，没有形成完整模型。
- 目标函数、约束条件、归一化和罚项分散得太开，评委很难在短时间内把完整模型拼出来。
- 简化模型用了，但没有说明简化依据。
- 正文里堆了很多中间计算过程，却没有突出真正关键结果。
- 图表解释写在对应图表之前，或图表与解释相隔多个段落，打断读者对“证据 -> 结论”的理解顺序。

# 为 `math-modeling-constraints` 新增内容的维护指南

## 用途
这份文档是给 Codex 在后续继续扩展 `math-modeling-constraints` 时使用的维护规程。以后如果需要继续往这个 skill 里新增触发词、约束整理规则、输出结构说明或风险提示，优先先读这份文档，再决定改哪里、怎么改。

## 什么时候应该新增内容
以下情况适合继续新增到这个 skill：
- 出现新的高频用户口语表达，导致当前 `description` 或 `when_to_use` 覆盖不足。
- 需要补新的约束整理规则，例如来源标注、优先级排序、软硬约束区分。
- 需要补新的约束表达方式，例如某类常见不等式写法、集合定义写法或变量说明要求。
- 发现新的常见跑偏情况，值得加入风险提示或维护说明。

以下情况通常不应该直接加到这个 skill：
- 某个具体模型的目标函数设计细节。
- 某一次会话的临时约束口径。
- 更适合放到 `math-modeling-objective-function-builder`、`math-modeling-brainstorm` 或其他专门数模 skill 的内容。
- 与代码实现强绑定的内容。

## 新内容应该加到哪里
新增内容时，先判断它属于哪一类，再放到对应区块：

| 新增内容类型 | 应放位置 |
|---|---|
| 触发词、用户口语表达、何时应该调用本 skill | frontmatter 的 `description` / `when_to_use` |
| 适用场景说明 | `什么时候优先用本 skill` |
| 通用证据链与逻辑要求 | `证据链与逻辑严谨性（必须遵守）` |
| 约束提取步骤、提问方式、范围确认 | `使用流程（一步一问）` |
| 约束输出结构与不等式表达规范 | `输出格式（结构说明，不依赖外部文件）` |
| 常见问题与混淆点 | `常见风险提示` |
| 低频、长说明、维护导向规则 | `references/` |

## 新增内容的判断流程
以后新增内容时，按下面顺序判断：

1. 先判断这是“触发优化”还是“约束方法规则补充”。
2. 再判断它是不是通用规则，还是只适用于某类题目或某一种模型。
3. 如果是通用规则，优先考虑放入主 `SKILL.md` 的现有区块。
4. 如果只是低频、长说明或维护说明，优先放进 `references/`，主文只留入口。
5. 如果会改变触发边界，必须同步检查 `description` 和 `when_to_use`。
6. 如果它更适合其他数模 skill，就不要硬塞进本 skill。

## 写法规范
- 解释“为什么这样整理约束”，不要只写“必须”。
- 新规则尽量短，优先补到已有区块，不轻易新开大区块。
- 不写一次性案例总结，不写叙事式历史。
- 能放进现有结构就不要重复再写一遍。
- 新增内容要优先提高约束提取的完整性、清晰度和可复核性，而不是增加篇幅。

## 修改前检查清单
- 这条内容是否真的是高频、可复用规则。
- 是否和已有区块重复。
- 是否本来属于别的数模 skill。
- 是否会改变触发边界。
- 是否需要同步调整 `description` 或 `when_to_use`。

## 修改后检查清单
- `description` 与 `when_to_use` 是否仍然清楚指向“约束提取与整理”。
- 新内容是否放在了正确区块。
- 主 `SKILL.md` 是否仍然简洁，没有被低频长说明压重。
- 是否引入新的重复表述。
- 是否仍然保持“先提取约束，再进入目标函数或代码”的定位。

## 常见错误
- 把约束提取 skill 写成整题建模 skill。
- 把目标函数或算法选择内容塞进约束 skill。
- 只列公式，不写约束来源和文字解释。
- 增加内容后不检查 `description` / `when_to_use`。
- 把一次性题面要求写成永久规则。

## 建议回归测试提示词
- “请把这道题的题面限制条件整理成可写进论文的约束清单。”
- “帮我把附件里的容量限制和时序限制写成不等式，并标注来源。”
- “我现在只有题面截图，先帮我提取约束条件，再告诉我哪些地方证据不足。”

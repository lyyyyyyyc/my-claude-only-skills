# 整题建模设计模式

## 用途与读取边界

本文件用于完整赛题或多问联动任务，帮助判断各问在整题中的作用、前后问如何传递信息、整题应采用什么递进架构，以及创新建议是否可实施、可比较、可验证。

局部单问不读取本文件。题型和具体模型方法仍由 `math-modeling-model-and-methods` 负责，本文件不替代模型选择。

## 子问题的八种流程角色

流程角色描述“本问在整题中负责什么”，不等同于预测、优化、分类等数学题型。同一问题可以有一个主要角色和一个次要角色，但必须说明主次关系。

| 流程角色 | 核心作用 | 常见输入 | 典型输出 | 对后续问题的作用 |
|---|---|---|---|---|
| `foundation` | 建立全题共用的基础定义、状态、几何关系或主模型 | 题面定义、附件数据、统一假设 | 公共变量、基础方程、统一口径 | 为后续各问提供共同底座 |
| `estimation` | 从数据或观测中估计未知参数、状态或分布 | 观测数据、基础模型 | 参数估计、置信区间、状态估计 | 作为后续计算的参数或输入 |
| `explanation` | 解释变量关系、机制或结果形成原因 | 数据、模型结果、机制假设 | 影响关系、机制解释、显著因素 | 支撑模型选择、结论解释或改进方向 |
| `prediction` | 预测未来数值、状态、类别或风险 | 历史数据、估计参数、外生变量 | 预测值、区间、概率或类别 | 作为后续决策和优化的情景输入 |
| `extension` | 在已有模型上增加新对象、因素、阶段或不确定性 | 前问模型和结果、新增条件 | 扩展模型、修正结果、适用范围变化 | 说明前问结论在新条件下如何变化 |
| `optimization` | 在目标和约束下寻找较优或最优方案 | 参数、预测结果、约束、初始方案 | 决策变量、目标值、可行方案 | 为最终方案选择提供候选结果 |
| `decision` | 综合模型结果形成可执行选择、排序或建议 | 预测、优化、评价和风险结果 | 最终方案、阈值、策略或行动建议 | 形成面向题目要求的最终交付 |
| `validation` | 独立检查模型、结果或方案是否可信 | 待验证结果、真实数据、守恒或可行性条件 | 误差、残差、稳定性或复核结论 | 决定结论能否保留、修正或回退 |

判断时先问：如果删除本问，整条建模链失去的是基础、参数、解释、预测、扩展、优化、决策还是验证？答案就是主要流程角色。

## 跨问传递的六类接口

跨问关系不能只写“问题二依赖问题一”，必须同时指出上游的具体输出和进入下游的方式。

| 接口类型 | 含义 | 应写清的内容 | 常见风险 |
|---|---|---|---|
| 参数 | 上游估计量进入下游公式或算法 | 参数名称、单位、取值或分布、来源问题 | 把估计值误当成无误差常数 |
| 基线 | 上游结果作为比较参照 | 基线方案、比较指标、统一数据范围 | 比较口径或计算预算不同 |
| 约束 | 上游结论限定下游可行域 | 约束形式、边界、软硬性质、来源 | 把经验结论静默写成题面硬约束 |
| 初始值 | 上游结果用于数值计算或搜索起点 | 初始状态、初始解、初始化范围 | 初值依赖导致局部结果却未说明 |
| 输入 | 上游输出直接成为下游数据或特征 | 字段、维度、时间范围、预处理口径 | 字段或时间粒度前后不一致 |
| 验证器 | 上游模型或条件用于检查下游结果 | 检查对象、判定标准、允许误差 | 验证与建模使用同一证据而不独立 |

推荐写法：`问题一输出的参数 θ 及其区间作为问题二目标函数的参数输入；问题二求得的方案再由问题一的机理方程复算其可行性。`

## 常见整题架构

### 机理 -> 计算 -> 修正

先建立能够解释系统的机理关系，再据此计算状态或结果，最后针对误差、边界效应或新增因素修正模型。三个阶段应沿用同一状态定义、坐标系和单位，并用修正前后的同口径结果证明修正是否有效。

### 估计 -> 预测 -> 决策

先由历史或观测数据估计参数，再用已锁定的参数产生预测，最后把预测值、预测区间或情景分布传给决策模型。必须说明估计误差和预测不确定性是否会改变最终决策，不能只把点预测当作精确未来值。

### 确定 -> 不确定 -> 鲁棒

先建立确定性基准模型，再识别哪些参数、需求或环境条件不确定，最后用情景、概率或不确定集合形成鲁棒方案。鲁棒模型应沿用原有核心约束，并与确定性方案比较目标损失和风险改善。

## 全文统一口径检查

完整路线确定后逐项检查：

1. 同一符号在不同问题中是否保持相同含义、索引范围和维度。
2. 单位、量纲、坐标系、方向约定和时间粒度是否一致。
3. 同一参数是否只估计一次并在后问明确复用；重新估计时是否说明原因。
4. 前问输出进入后问时是否保留对象范围、时间范围、误差和适用条件。
5. 目标方向、评价指标和可行性定义是否前后一致。
6. 后问新增的假设、变量、约束或风险是否与前问内容明确区分。
7. 后问若改变口径，是否写明改变位置、理由以及对已有结果的影响。

## 创新提案检查表

创新必须是相对于基础方案的可实施改动，并能通过对照实验判断是否产生收益。每项创新至少填写：

| 检查项 | 必须回答的问题 |
|---|---|
| 基础方案 | 不采用该创新时，原始方案是什么？ |
| 改动组件 | 具体改变了模型、数据、约束、目标、求解还是验证中的哪一部分？ |
| 实现步骤 | 需要新增哪些变量、公式、算法步骤或数据处理？ |
| 可测收益 | 预期改善哪个指标，改善方向是什么？ |
| 工作量 | 新增的数据、代码、实验和论文篇幅是否能在竞赛时间内完成？ |
| 对照实验 | 如何在相同数据、约束、指标和预算下与基础方案比较？ |
| 风险 | 哪些假设可能不成立，最可能失败在哪里？ |
| `fallback` | 创新失败、时间不足或结果不稳定时退回哪个方案？ |
| 影响问题 | 改动会影响哪些子问题、接口、结果和论文章节？ |

以下做法本身不能算创新：使用遗传算法、模型融合、增加变量、增加可视化。只有说明相对基础方案改了什么、为什么适合本题，并用同口径实验验证收益后，才能作为创新候选。

# 为 `math-modeling-brainstorm` 新增内容的维护指南

## 用途
这份文档是给 Codex 维护 `math-modeling-brainstorm` 时使用的操作规程。以后如果需要继续往这个 skill 里新增规则、补触发词、增加分流逻辑、补高风险约束或修正常见跑偏行为，优先先读这份文档，再决定改哪里、怎么改。

## 什么时候应该新增内容
以下情况适合继续新增到这个 skill：
- 出现新的高频用户指令表达，导致当前 `description` 或 `when_to_use` 覆盖不足。
- 出现新的数模通用分析规则，且适用于多类题目，而不是某一种具体模型。
- 需要补新的分流规则，帮助本 skill 更好地把任务交给其他数模 skill。
- 需要补新的高风险执行约束，例如代码、Notebook、优化算法、交付评审等场景。
- 发现新的常见跑偏场景，值得加入 `Common Mistakes` 或默认响应协议。

以下情况通常不应该直接加到这个 skill：
- 只适用于单一题型或单一模型的细节。
- 某一个具体模型的方法步骤、公式推导或参数技巧。
- 只针对某一次会话的临时要求。
- 更适合放到其他专门数模 skill 的内容。

## 新内容应该加到哪里
新增内容时，先判断它属于哪一类，再放到对应区块：

| 新增内容类型 | 应放位置 |
|---|---|
| 触发词、用户口语表达、何时应该调用本 skill | frontmatter 的 `description` / `when_to_use` |
| Codex 触发后第一步该做什么 | `第一优先动作` / `默认响应协议` |
| 通用思维规则、证据链要求、论文化理由要求 | `证据链与逻辑严谨性` |
| 多步任务的停顿、确认和推进方式 | `多步任务协作约束` |
| 建模前必须向用户确认的信息 | `模型设计/编程前强制澄清` |
| 只在高风险任务中生效的规则 | `高风险任务附加约束` |
| 容易跑偏的行为或错误倾向 | `Common Mistakes` |
| 用户常见起手话术或不会提问时的引导 | `用户起步提示` |

## 新增内容的判断流程
以后新增内容时，按下面顺序判断：

1. 先判断这是“触发优化”还是“执行约束”。
2. 再判断它是“通用规则”还是“仅某类任务适用”。
3. 如果是通用规则，优先考虑放入主 `SKILL.md` 现有区块。
4. 如果只是低频、长说明或维护说明，优先放进 `references/`，主文只留入口。
5. 如果这条内容会改变 skill 的触发边界，必须同步检查 `description` 和 `when_to_use`。
6. 如果它更适合其他数模 skill，就不要硬塞进 `math-modeling-brainstorm`。

## 写法规范
根据 `skill-creator` 和 `writing-skills`，新增内容时遵守以下写法：
- 解释“为什么”，不要只堆“必须”。
- 新规则尽量短，优先补充已有区块，不轻易新开大区块。
- 对高风险规则要写清适用条件，不要扩大到所有任务。
- 不写叙事式历史，不写一次性案例总结。
- 能归入已有结构就不要重复写一遍。
- 新增内容要优先减少跑偏，而不是单纯增加篇幅。
- 如果内容很长、很低频、很维护导向，优先放 `references/`，不要把主 `SKILL.md` 前半段写重。

## 修改前检查清单
新增前先检查：
- 这条内容是否真的是高频、可复用规则。
- 是否和已有区块重复。
- 是否本来属于别的数模 skill。
- 是否会改变触发边界。
- 是否需要补 `Common Mistakes` 或 `用户起步提示`。

## 修改后检查清单
新增后再检查：
- 主 skill 的结构顺序是否仍然稳定，前半段是否仍然以“先分析、先拆题”为主。
- frontmatter 是否需要同步更新。
- 新内容是否放在了正确层级。
- 是否引入了新的重复表述。
- 是否需要补 2–3 条回归测试提示词，验证新增内容真的有用。

## 常见错误
- 把具体模型知识直接塞进通用头脑风暴 skill。
- 把低频超长规则放进主文前半段。
- 只加硬规则，不写触发条件和作用范围。
- 增加内容后不检查 `description` / `when_to_use`。
- 把一次性任务要求写成永久规则。

## 维护时的默认原则
- 能少改就少改，优先最小改动。
- 先补触发与分流，再补执行细则。
- 先减少跑偏，再增加覆盖面。
- 如果新增内容会让主文变重，优先把长说明放进 `references/`。

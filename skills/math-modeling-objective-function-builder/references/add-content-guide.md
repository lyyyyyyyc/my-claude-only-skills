# 为 `math-modeling-objective-function-builder` 新增内容的维护指南

## 用途
这份文档是给 Codex 在后续继续扩展 `math-modeling-objective-function-builder` 时使用的操作规程。以后如果需要继续往这个 skill 里新增触发词、补目标函数写法规则、细化多目标组合方式或补维护说明，优先先读这份文档，再决定改哪里、怎么改。

## 什么时候应该新增内容
以下情况适合继续新增到这个 skill：
- 出现新的高频用户口语表达，导致当前 `description` 或 `when_to_use` 覆盖不足。
- 需要补新的目标函数构建规则，例如多目标组合、归一化、权重解释、目标方向判断。
- 需要补新的“目标函数文字解释”要求，使输出更适合论文正文。
- 发现新的常见跑偏错误，例如不确认任务范围、只给公式不解释、忽略约束来源。

以下情况通常不应该直接加到这个 skill：
- 某一个具体模型或算法的求解细节。
- 某一个题目的临时目标函数写法偏好。
- 更适合放到 `math-modeling-brainstorm`、`math-modeling-constraints` 或代码类 skill 的内容。
- 只适用于单次会话的临时要求。

## 新内容应该加到哪里
新增内容时，先判断它属于哪一类，再放到对应区块：

| 新增内容类型 | 应放位置 |
|---|---|
| 触发词、用户口语表达、何时应该调用本 skill | frontmatter 的 `description` / `when_to_use` |
| 首次响应应该先确认什么 | `什么时候优先用本 skill` / `第一优先动作` |
| 通用严谨性要求 | `证据链与逻辑严谨性（必须遵守）` |
| 目标函数构建步骤 | `固定流程（一步一问，优先选择题）` |
| 输出结构与公式表达要求 | `输出规范（推荐 Markdown 文档）` |
| 容易跑偏的问题 | `Common Mistakes` |
| 低频、长说明、维护导向内容 | `references/` |

## 新增内容的判断流程
以后新增内容时，按下面顺序判断：

1. 先判断这是“触发优化”还是“目标函数知识扩展”。
2. 再判断它是“通用规则”还是“某类任务专用”。
3. 如果是通用规则，优先放到主 `SKILL.md` 的现有区块。
4. 如果只是低频、长说明或维护说明，优先放进 `references/`，主文只留入口。
5. 如果这条内容会改变 skill 的触发边界，必须同步检查 `description` 和 `when_to_use`。
6. 如果它更适合别的数模 skill，就不要硬塞进本 skill。

## 写法规范
- 解释“为什么”，不要只堆“必须”。
- 新规则尽量短，优先补进已有区块，不轻易新开大区块。
- 目标函数规则要同时说明数学表达和论文表达，不要只保留公式视角。
- 不写叙事式历史，不写一次性案例总结。
- 能归入已有结构就不要重复写一遍。
- 新增内容要优先减少跑偏，而不是单纯增加篇幅。

## 修改前检查清单
- 这条内容是否真的是高频、可复用规则。
- 是否和已有区块重复。
- 是否本来属于别的数模 skill。
- 是否会改变触发边界。
- 是否需要补 `Common Mistakes` 或 `第一优先动作`。

## 修改后检查清单
- frontmatter 是否需要同步更新。
- 新内容是否放在了正确层级。
- 主 `SKILL.md` 是否仍然保持“先确认范围，再构建目标函数”的顺序。
- 是否引入新的重复表述。
- 是否需要补 2–3 条测试提示词，方便后续人工回归。

## 常见错误
- 没确认题目范围就直接写目标函数。
- 把目标函数构建 skill 写成整题建模 skill。
- 只写公式，不写文字解释和权重含义。
- 把约束条件的内容硬塞进目标函数 skill。
- 增加内容后不检查 `description` / `when_to_use`。

## 维护时的默认原则
- 能少改就少改，优先最小改动。
- 先补触发与入口，再补规则细节。
- 先减少跑偏，再增加覆盖面。
- 如果新增内容很长，优先下沉到 `references/`。

## 建议回归测试提示词
- “这题目标函数怎么写？先帮我把题意变成优化目标。”
- “这个目标到底该最大化还是最小化，你先判断并解释。”
- “多目标怎么合起来更合适？先别写代码，只写目标函数和理由。”

> 调用 `$math-modeling-code-simplifier` 后，默认优先读取本文件；不能只凭主 `SKILL.md` 的简述或历史记忆决定附录写法。

## 目标
- 把数模代码整理成论文附录里常见的独立 `.py` 文件。
- 风格更接近本科答卷，而不是成熟工程项目。
- 保证“可复现、可审查、可提交”优先于“高度优雅、极致抽象”。

## 文件命名建议
- 文件名尽量使用 ASCII，避免中文文件名。
- 推荐命名格式：
  - `appendix_3_main_model.py`
  - `appendix_4_risk_extension.py`
  - `appendix_5_correlation_analysis.py`
- 若用户已给定附录号和名称，优先遵从用户命名口径。

## 注释密度
- 注释必须是中文。
- 必须严格区分“注释中文、代码英文”：中文解释写在注释里，代码主体、变量名、函数名、路径名和主字符串口径默认保持英文或拼音。
- 只保留关键注释，不写“显而易见”的废话注释。
- 默认注释深度是“中等程度”：
  - 不走逐行碎讲；
  - 也不能只留文件头一条总说明；
  - 重点是让读者能快速知道“这一段/这个函数主要是干什么的”。
- 注释语气可以略微大白话一点，但核心还是解释功能，不要写成口水话。
- 注释密度宁可偏多，也不要偏少；读者应能直接看出每个代码块在干什么。
- 每个关键代码块前，至少说明：
  - 这一步做什么
  - 输入/输出是什么
  - 对结果有什么影响或风险
- 函数和类定义前，默认也补一句中文功能说明，优先解释“主要负责什么”“在主流程里起什么作用”。
- 对数据读取、字段整理、核心求解、结果导出、主入口这几类函数，默认优先补说明。
- 默认先解释“功能”和“作用”，不默认写成长篇参数手册；只有用户明确要求更细时，才继续加深。
- 不要求每一行都加注释。
- 对超过一个屏幕长度的附录，必须显式切分段落注释，例如“数据读取”“字段映射”“主计算”“结果导出”。
- 段落注释只写标题本身，不要再加 `# ======`、`# -----` 这类装饰边框。
- 段落注释默认不写 `1.`、`2.`、`3.` 这类编号，避免模板感过强；直接写成 `# 数据读取`、`# 主计算` 即可。
- 注释要解释当前附录的具体动作，不要写“路径怎么找”“主流程按什么顺序展开”这类对任何附录都能套用的模板化说明。
- 如果一条注释拿到遗传算法、LSTM、绘图、需求构造四个附录里都能原封不动复用，通常说明它太空泛，应该删掉或改成更贴近当前功能的说明。

## 注释写完后的可读性复查
- 随机高斯删字功能已禁用，不自动调用 `../scripts/random_comment_pruner.py`，也不以其他方式模拟随机删字。
- 每个附录 `.py` 文件完成代码与中文注释后，检查注释是否完整、通顺并准确解释代码；修正缺字、歧义与错误说明。
- 上述注释密度、完整性和可读性要求始终适用于最终交付。
- `examples/commented_example_double_pruned.py` 仅为历史示例，不是处理器，也不作为最终注释质量模板。
- 复查后仍须编译并验证核心功能；不再要求生成随机处理后的副本或报告删除数量。

## 禁止保留的内容
- 不要在最终附录正文里保留 `# ===== 来源 Notebook: ... =====` 这类溯源标记。
- 不要保留 `# ==============================`、`# ----------------------------` 这类纯装饰分隔行。
- 不要保留 `# 固定通过当前脚本位置反推项目根目录，不依赖运行时当前工作目录。` 这类路径模板注释。
- 不要保留 `# 主流程统一按“读取输入 -> 清洗整理 -> 计算求解/绘图 -> 导出结果”顺序展开。` 这类流程模板注释。
- 不要保留 `u8d77_point`、`u5b9a_u4f4d_project_root` 这类半转码变量。
- 不要把 `Path.cwd()` 向上查找项目根目录的 Notebook 临时逻辑直接带进最终附录；默认应直接基于 `__file__` 反推根目录。

## 本科答卷风格
- 优先小到中等粒度函数，不追求复杂抽象。
- 允许顺序式写法、显式中间变量和朴素循环。
- 允许为清晰性保留少量重复代码。
- 允许直接写清业务逻辑，不强求工具函数层层封装。

## 允许的朴素写法
- 用 `for` 循环逐步累计目标值、惩罚项、统计量。
- 用几个明确的 `if/elif/else` 直接表达场景分支。
- 把风险项、相关性项、后处理项顺序加到主模型上。
- 为了让单个附录能独立运行，重复数据读取和参数区是可接受的。

## 避免的过度成熟写法
- 不主动引入复杂配置系统、插件式架构或深层模块拆分。
- 不主动引入装饰器体系、工厂模式、策略模式、元编程。
- 不主动为了“高级感”强行向量化本来就不复杂的业务逻辑。
- 不主动引入大而全日志系统、CLI 框架、复杂异常体系。
- 不把简单附录代码包装成大型软件项目。

## 扩展附录写法
- 算法扩展版允许复制前一附录的核心代码，再追加：
  - 风险项
  - 相关性项
  - 敏感性分析
  - 对比实验
- 这种“基于前一附录扩展”的写法符合论文附录习惯，允许保留必要重复。

## 独立运行要求
- 每个附录默认应能单独运行。
- 若多个附录使用同一数据源，允许每个附录各自读取一次数据。
- 若附录依赖公共映射表或参数，允许直接写在本文件顶部，不强求外部依赖。

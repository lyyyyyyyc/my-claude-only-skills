# 为 `math-modeling-code-simplifier` 新增内容的维护指南

## 用途
这份文档是给 Codex 在后续继续扩展 `math-modeling-code-simplifier` 时使用的维护规程。以后如果需要继续往这个 skill 里新增工程化规则、补充触发说明、细化输出清单或增加代码规范，优先先读这份文档，再决定改哪里、怎么改。

## 什么时候应该新增内容
以下情况适合继续新增到这个 skill：
- 出现新的高频“代码简化/工程化”需求表达，但仍然是在用户显式调用 `$math-modeling-code-simplifier` 的前提下。
- 需要补新的工程化规范，例如目录结构、配置集中化、结果落盘、日志口径统一。
- 需要补新的最小交付文件清单或审查友好输出要求。
- 发现新的常见跑偏错误，例如只改风格不改复现性、只报目标值不报可行性。

以下情况通常不应该直接加到这个 skill：
- 与某一种具体模型强绑定的方法细节。
- 不需要用户显式调用也想自动触发的宽触发规则。
- 某一次会话的临时编码偏好。
- 更适合放到 `math-modeling-intelligent-optimization-coder`、`math-modeling-data-preprocessing` 或其他专门数模 skill 的内容。

## 新内容应该加到哪里
新增内容时，先判断它属于哪一类，再放到对应区块：

| 新增内容类型 | 应放位置 |
|---|---|
| 显式调用边界、触发补充说明 | frontmatter 的 `description` / `when_to_use`，以及 `触发边界（最高优先级）` |
| 工程化目标与适用范围 | `概述` |
| 通用工程化原则 | `核心经验（提炼版）` |
| 文件选择、`.py/.ipynb` 使用边界 | `文件形态规则（硬性）` |
| 参数、入口、路径、随机种子、输出格式 | `代码结构规范（硬性）` |
| 注释、约束编号、回退规则说明 | `注释习惯（按优秀论文代码风格）` |
| 随机删字功能的禁用状态与重新启用边界 | `references/comment-pruning-workflow.md`，主文保留禁用规则，不设置自动调用路由 |
| 改造步骤 | `简化改造流程（执行顺序）` |
| 交付文件要求 | `最小输出清单（提交前）` |
| 低频、长说明、维护导向规则 | `references/` |

## 新增内容的判断流程
以后新增内容时，按下面顺序判断：

1. 先判断这是“触发说明补充”还是“工程化规则补充”。
2. 再判断它是不是通用规则，还是只适用于某一类模型或某一次任务。
3. 如果会改变触发边界，必须先确认是否仍然保持“只有显式调用才触发”。
4. 如果只是低频长说明，优先放进 `references/`，主文只留入口。
5. 如果这条内容更适合别的数模 skill，就不要硬塞进本 skill。

## 写法规范
- 不要破坏“仅显式调用才触发”的最高优先级边界。
- 解释“为什么这样改”，不要只堆“必须”。
- 新规则优先短句化、归入已有区块，不轻易新开大区块。
- 不写一次性案例总结，不写叙事式历史。
- 新增内容要优先提升复现性、可审查性、可提交性，而不是只让代码更“好看”。
- 若某个 `references/` 文件已经是该 skill 的默认执行依据，就不要在主文里只写“按需读取”；应明确写成“默认优先读取”或“默认必读”。
- 若某个高频 reference 会直接影响输出质量，主 `SKILL.md` 里要写清具体文件名和读取时机，不能只笼统说“参考 references/”。
- 注释后处理规则必须同时核对 `SKILL.md`、`appendix-code-style.md`、`comment-pruning-workflow.md` 与 `scripts/random_comment_pruner.py`，不能只改其中一处。
- 若改动了 reference 的读取优先级，必须同步检查主 `SKILL.md` 与相关 reference 文件本身，避免再次出现主文强调不够、reference 形同虚设的问题。

## 修改前检查清单
- 这条内容是否真的是高频、可复用规则。
- 是否会破坏显式触发边界。
- 是否和已有区块重复。
- 是否本来属于别的数模 skill。
- 是否需要同步调整 `description` 或 `when_to_use`。

## 修改后检查清单
- frontmatter 是否仍然清楚强调“仅显式调用才触发”。
- 新内容是否放在了正确区块。
- 主 `SKILL.md` 是否仍然简洁，没有被低频长说明压重。
- 是否引入新的重复表述。
- 是否仍然清楚区分“代码工程化”与“具体算法求解”。

## 常见错误
- 为了提高触发率，错误放宽成自动触发。
- 把具体模型知识直接塞进代码简化 skill。
- 只改代码风格，不补复现与审查输出。
- 增加内容后不检查 `description` / `when_to_use`。
- 把一次性项目习惯写成永久规则。

## 维护时的默认原则
- 能少改就少改，优先最小改动。
- 先守住显式触发边界，再补工程化细则。
- 先提升复现性和可审查性，再考虑美化与扩展。
- 如果新增内容很长，优先下沉到 `references/`。

只在用户要求问题分析框架、算法步骤、模型架构、数据流、指标层级或求解流程图时读取本文件。

# 方法逻辑图与流程图

## 任务边界

- 本文件把论文、题目、伪代码或已有模型中的逻辑关系变成可读图形。
- 流程图是表达层，不是重新设计模型。不得添加原文没有支持的变量、步骤、判断条件、反馈回路、因果关系或结论。
- 用户仅要求“给建议”时，交付图型建议和节点清单；只有明确要求绘制时才生成图。
- 插入论文、更新图号、更新交叉引用或改写正文属于另行授权的文档编辑任务。

## 先判图的类型

1. `方法流程图`：输入、处理、判断、输出与反馈的先后关系。
2. `数据流图`：数据来源、清洗、变换、存储、模型输入和结果输出。
3. `模型框架图`：模块、变量层、约束层和结果层之间的结构关系。
4. `算法流程图`：初始化、迭代步骤、判断条件、终止条件和输出。
5. `指标层级图`：目标、准则、指标与子指标的从属关系。

先选图的逻辑语义，再选形状和颜色；不要因所有图都有方框和箭头就把它们画成同一种流程图。

## 证据映射

绘制前先形成节点和连边清单。每项至少记录：

| 对象 | 类型 | 精炼标签 | 来源 | 未确认内容 |
| --- | --- | --- | --- | --- |
| 节点 | 输入 / 处理 / 判断 / 模块 / 输出 | 动词或名词短语 | 原文段落、公式、表格或已有结果 | 不补写 |
| 连边 | 控制 / 数据 / 条件 / 反馈 / 从属 | 必要时说明语义 | 同上 | 不猜测方向 |

- 输入、已知条件和数据源可作为输入节点。
- 分析、计算、优化和处理可作为过程或模块节点。
- 真正决定后续路径的条件可作为判断节点，并写明各分支去向。
- 结果、方案、报告或模型输出可作为输出节点。
- 只有原文明确存在迭代或返回逻辑时才画反馈箭头。

## 箭头与关系边界

- `控制流` 表示执行先后或判断分支。
- `数据流` 表示数据或中间结果的传递。
- `从属关系` 表示层级归属，通常更适合树状或层级图。
- `因果关系` 只有在题目、模型假设或经验证分析明确支持时才使用；先后发生、相关性或公式引用不自动构成因果箭头。
- 箭头方向、箭头标签和线型必须服务于上述语义；没有额外语义时，普通连线已足够。

## 版式与可读性

- 先确定主阅读方向，通常自上而下或自左向右，并在全图保持一致。
- 节点按逻辑层级和阅读顺序对齐；避免无意义的交叉箭头。复杂系统可拆成总览图和局部图。
- 节点文字使用能忠实概括原文的短语。文字长度、是否中英双语、分区数量和节点形状由最终尺寸与读者决定，不采用固定词数或固定分区数。
- 分区可用于区分数据、模型、求解、验证或输出等真实模块；没有真实模块边界时不强行上色分区。
- 颜色、形状和线型是辅助编码，不能掩盖箭头语义。实际绘制时遵守主文件的字体、白底、布局和可读性门禁。

## 质量检查

交付前检查：

1. 核心输入、处理、判断、输出和必要反馈是否都能回溯到来源。
2. 每条箭头的方向和语义是否可解释，是否把先后或关联误画成因果。
3. 主流程方向是否稳定，交叉、绕行和文字溢出是否已处理。
4. 节点和连边是否遗漏、重复或改写了原模型逻辑。
5. 图中术语、编号、图注与论文现有口径是否一致。

质量检查结果应按“通过 / 失败 / 不适用 / 未验证”标记。关键来源缺失时，不将整图描述为“逻辑完整”。

## 不要做什么

- 不要因章节较长或没有流程图就自动生成流程图。
- 不要用固定颜色、双语、节点数或分区数冒充质量。
- 不要为了图面整齐删除必要分支，也不要为了丰富图面新增不存在的反馈回路。
- 不要把算法步骤图、数据流图、因果图和指标层级图混用。

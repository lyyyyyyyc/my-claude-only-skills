# 数学建模附录代码技能

## 触发边界（最高优先级）
- 只有当用户在当前轮消息里显式调用 `$math-modeling-code-simplifier` 时，才允许使用本 skill。
- 若用户未显式调用本 skill，即使任务内容很匹配，也必须不使用本 skill。
- 本节优先级高于其他所有触发描述。

## 概述
- 第一动作必须调用 `math-modeling-brainstorm`，先把代码对应的题目范围、目标口径、约束口径和交付边界对齐，再开始改写附录代码。
- 目标不是把代码做成成熟工程项目，而是把整题代码整理成**论文附录风格的独立 `.py` 文件集合**。
- 默认产物是一个个单独、可单独运行、可复核的附录 `.py` 文件，而不是一个高度封装的大项目。
- 优先保证“功能可复现、逻辑可审查、论文可提交”，再考虑风格统一和命名整理。

## 核心原则（提炼版）
- 先保功能一致，再改写风格：
  - 不为了改写得更像附录代码而擅自改动模型口径、计算逻辑、约束定义或结果含义。
- 先拆附录边界，再改命名：
  - 先确认每个附录负责什么，再处理变量命名和代码风格。
- 先去中文化，再做拼音协商：
  - 先把代码主体里的中文变量、中文函数名、中文字段口径清干净，再处理复杂英文变量是否转拼音。
- 先保证独立运行，再考虑去重：
  - 若为了让某个附录可单独运行而需要保留少量重复代码，允许这样做。

## 默认交付形态（硬性）
- 默认交付为多个独立 `.py` 文件，不是单个大脚本，也不是 `.ipynb`。
- 每个附录对应一个独立 `.py` 文件，并且默认可单独运行。
- 每个附录文件开头必须用中文注释写明“附录几 + 名称”。
- 默认允许少量重复代码，不强求抽出公共工具层。
- 若原始代码在 `.ipynb` 中，必须沉淀出同功能 `.py` 版本；除非用户明确要求保留 Notebook 展示，否则不以 `.ipynb` 为主交付。

## 调用时的强制对齐流程（硬性）
1. 先通过 `math-modeling-brainstorm` 对齐题目范围、目标口径、约束口径和交付边界。
2. 先确认当前代码需要拆成几个附录文件。
3. 先询问附录顺序，并给出推荐顺序；在顺序未确认前，不直接开始生成附录代码。
4. 先确认哪些代码块归入哪个附录，避免把主模型、扩展模型、敏感性分析、后处理混在一起。
5. 先在对话框列出“建议转拼音的复杂英文变量”和“必须去中文化的中文变量”。
6. 等用户选定变量命名后，再生成附录代码。
7. 若用户未提供附录顺序，默认按推荐顺序推进，并明确告诉用户本次采用了哪套默认顺序。

## 默认附录顺序推荐
- 默认推荐顺序：`主模型 -> 风险扩展 -> 相关性/敏感性 -> 对比实验 -> 后处理/导出`
- 若代码依赖链与默认顺序不一致，必须先说明原因，再调整顺序。
- 若用户已经给出附录编号和名称，优先遵从用户编号；仅在明显冲突时给出修正建议。

## 附录代码风格规则（硬性）
- 代码风格默认是“本科答卷风格”，不是成熟工程代码。
- 优先清楚直接、可复现、函数拆分适中；允许朴素 `if/for`、顺序写法和少量重复。
- 不主动追求向量化、设计模式、复杂抽象、过度封装、过深模块分层。
- 注释只保留关键注释，且必须是中文。
- 必须严格区分“注释中文、代码英文”：中文只允许出现在注释和最终导出展示口径里，代码主体、变量名、函数名、路径名、字符串主口径默认保持英文或拼音。
- 默认注释深度是“中等程度中文注释”：
  - 不是逐行讲解；
  - 也不是只在文件头写一条总说明就结束；
  - 默认要让读者快速看懂“这一段大概在干什么”。
- 默认注释语气可以偏大白话一点，但不能油滑；优先像在给队友、评委或初学者解释“这一步到底是干嘛的”。
- 注释密度偏高：每个关键代码块前都要有“这一步做什么、输入输出是什么、对结果有什么影响”的中文注释。
- 函数和类默认也要补一句中文功能说明，重点解释“这个函数/类主要负责什么”，而不是机械复述函数名。
- 主流程函数、数据读取函数、字段整理函数、核心计算函数、结果导出函数，默认都属于必须优先补说明的对象。
- 默认优先解释“功能”和“作用位置”，不默认展开成逐参数、逐行、教科书式长注释；只有用户明确要求更细时，才继续加深。
- 若某个附录超过一个屏幕长度，必须显式分出“数据读取、字段映射、参数区、核心计算、结果导出”等段落注释，不能只在文件头写一条总注释。
- 段落注释禁止写成 `# ========`、`# ----------------`、前后各一条装饰横线包住标题这一类边框样式；最终只保留一句自然中文标题注释即可。
- 段落标题默认不写 `1.`、`2.` 这类机械编号；除非用户明确要求保留编号，否则直接写成 `# 全局配置与固定参数`、`# 结果导出` 这类自然标题。
- 注释必须服务于当前附录的具体功能，优先解释遗传算法、LSTM、需求构造、结果导出这类真实业务或算法动作；与具体功能无关的模板化说明不要写。
- 禁止保留 `# 固定通过当前脚本位置反推项目根目录，不依赖运行时当前工作目录。`、`# 主流程统一按“读取输入 -> 清洗整理 -> 计算求解/绘图 -> 导出结果”顺序展开。` 这类通用框架说明注释，因为它们不解释当前附录到底在做什么。
- 除注释外，代码中尽量不要出现中文。
- 若原代码中本身有中文变量、中文函数名、中文中间量，必须统一改成简单英文字母或拼音。
- 自动改名过程中如果出现 `u8d77_point`、`u5b9a_u4f4d_project_root` 这类半转码变量，禁止直接保留到最终交付，必须继续改成正常英文或拼音命名。
- 复杂英文变量不直接擅自改拼音，必须先给用户候选清单供其选择。
- 简单变量允许保留英文或短字母名；不要为了追求拼音而把所有变量都改成冗长拼音。
- 若用户希望“更像学生现场写出来的版本”，可以进一步减少抽象；但默认仍要保证可复现和可核查。
- 禁止在最终附录中保留 `# ===== 来源 Notebook: ... =====` 之类的溯源标记；来源关系应写入说明文档，而不是写进附录代码正文。
- 禁止在最终附录中保留 `# ==============================`、`# ----------------------------` 这类纯装饰分隔行，即使中间夹着有效标题也不保留。
- 禁止在最终附录中保留“路径解析口径说明”“主流程统一顺序说明”这类脱离业务上下文的模板化注释。
- 项目根目录默认直接基于 `__file__` 反推，不使用 `Path.cwd()` 向上查找再 `raise RuntimeError("未能定位项目根目录")` 这种 Notebook 口径写法；只有用户明确要求兼容多运行入口时，才允许保留回退查找逻辑。

## 中文数据去中文化规则（硬性）
- 若原始 Excel 列名、sheet 字段、类别值为中文，读取后第一步先统一转成英文或拼音字段。
- 后续主体逻辑尽量不再出现中文字面量，尤其不要把中文列名散落在核心计算区。
- 必要时允许在文件开头集中建立一次映射表，但主体计算区不再散落中文。
- 若论文最终导出的表格标题、表头或类别值必须保留中文，应在“导出前最后一步”再映射回中文，而不是把中文字段贯穿整个主计算链路。
- 默认策略如下：
  - 列名立刻重命名；
  - 关键类别值尽量编码成英文、拼音或编号；
  - 注释中解释原中文含义；
  - 若无法完全去除中文类别值，必须把中文控制在映射区，而不是计算主链路中。

## 变量命名协商协议（硬性）
- 调用时必须先输出一份“变量命名候选表”，再进入最终代码生成。
- 候选表至少分三类：
  - 建议保留英文的变量
  - 建议改成拼音的复杂英文变量
  - 必须去掉中文的中文变量
- 同时必须在对话框说明处理原则：
  - 为什么这个变量建议拼音
  - 为什么这个变量保留英文更稳
  - 为什么某些中文变量必须改
- 只有在用户选完后，才确定最终命名方案。
- 若用户不细选，则默认只改最明显的复杂长英文变量与全部中文变量。
- 不得随意改动第三方库 API、标准数学符号、广泛通用缩写或会显著降低可读性的短变量名。

## 代码结构规范（硬性）
- 每个附录文件默认采用以下顺序：
  - 文件头注释（附录几 + 名称）
  - `import`
  - 根目录与路径区
  - 数据读取
  - 字段/类别重命名映射
  - 参数区
  - 函数区
  - 主流程区
- 统一入口：
  - `if __name__ == "__main__": main()`
- 路径、随机种子、关键参数集中放在文件前部，不散落硬编码。
- 路径区默认写成 `root_dir = Path(__file__).resolve().parents[2]` 一类稳定口径，再从 `root_dir / "Solve" / ...` 派生，不依赖当前工作目录。
- 若某个附录需要独立运行，允许在该附录中重复写入数据读取、参数定义和基础函数。
- 不要求每个附录都抽出统一公共模块；“独立可运行”优先于“优雅复用”。

## 附录改写流程（执行顺序）
1. 对齐题目与代码边界。
2. 默认先读取并落实 `references/appendix-code-style.md` 与 `references/variable-renaming-guide.md` 的规则。
3. 划分附录数量、名称和顺序。
4. 输出变量命名候选表并等待用户选择。
5. 清理中文变量、中文函数名和中文字段口径。
6. 按附录风格改写每个独立 `.py` 文件。
7. 附录代码写完后，必须调用 `systematic-debugging`，按“先核查约束是否真的达成，再宣布完成”的口径做收尾复查。
8. 逐个检查附录是否能单独运行、是否仍可复现原功能，并核查用户额外要求是否真正落地。

## 完成后的强制复查（硬性）
- 完成附录改写后，必须转入 `systematic-debugging` 的流程做证据化复查，不能只凭肉眼扫一遍就宣布完成。
- 默认至少检查以下事项：
  - 代码中是否还残留中文字符
  - 用户要求去掉的注释、模板化说明、装饰分隔线是否真的清零
  - 是否真正做到“注释中文、代码英文”，即中文是否只出现在注释或最终展示口径中
  - 语法编译是否通过
  - 若涉及路径、字段映射、结果导出，相关改动是否仍然可运行
- 若用户本轮明确要求“源码里不能出现中文”，则复查时必须额外给出“中文字符搜索结果”为 0 的证据。

## 最小输出清单（提交前）

- 每个附录文件开头的“附录几 + 名称”中文注释

- 若涉及中文字段去中文化，文件内应包含集中映射区
- 对话框中的变量命名候选表与最终命名确认结果
- `systematic-debugging` 复查后的关键结论，至少包括：约束是否做到位、是否还有中文残留、语法是否通过。
